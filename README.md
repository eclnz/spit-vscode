# SPIT for VS Code

This local extension provides syntax highlighting and shows SPIT validation errors as you edit `.spit` pipelines, `.spitin` recipes, `.spitout` inputs and `.spitenv` tools files, and explains SPIT's words and a pipeline's names on hover. A `.spitout`'s headers (`sources:`, `source_paths:`, `contexts:`, `removed:`, `verdicts:`), every keyword (`require`, `exclude`, `missing`, `has`, `many`, `vary`, `where`, `same`, `each`, `min`, `verify`, `check` and `review` with the name they declare, `use`, `from`, `as`, `source`, `dimensions`, `types` with its `strict` or `standard` setting, `type` with the type and parameters it declares, `operation`, `command`, `resources` with the `cores=` and `memory=` each job of an operation needs (`resources align: cores=8, memory=16G`), `tool` with the tools it declares, `uses` with the operation it names and its tools, and the `!` that removes one (`uses register: fsl, !mrtrix3`), `anchored` with the operations it marks, alone or in an `anchored:` block (`anchored feat, group_feat`), `path`, `default` with the `path:`, `ext:`, `check:`, `review:`, `uses:` and `entities` defaults it sets, alone or in a `default:` block, `separated`, `stage`, a recipe's `pipeline` and `tools from` lines, the `root` and `output` lines of a pipeline, recipe or `.spitout`, and a `.spitenv`'s `tools:` block with each tool's name and the `probe` that identifies it), stage names, product and operation names, types (including `<generic>` parameters), a `many` input's minimum beside it (`days: many Series @min(2)`), the extension after an operation's output type (`-> Transform .mat`) and an output written `beside` another output or an input (`mask: Image "_mask.nii.gz" beside brain`, `-> Fai +.fai beside fasta`) or a source (`source events : Events .tsv [sub]`, `source gps : Track .gpx`, `source fai : Fai +.fai beside reference`), the `here` that ends a source kept beside the pipeline (`source plotter : Script .py here`), with the `+` that appends a suffix to the whole file name, the `/` after a type that makes a source or an output a folder (`source dicom : Dicom / [sub]`, `-> Zarr .zarr/`), dimension lists (`[site, device]`), `{placeholder}` text in commands and paths, the `<` and `>` that connect a command's stdin and stdout (`command count: wc -l < {table} > {@output}`), the shape after a source placeholder's colon (`{date:date}`, `{run:digits}`, `{year:year}`; see [Shapes on a source placeholder](https://github.com/eclnz/spit/blob/main/docs/language-reference.md#shapes-on-a-source-placeholder)) in a path rule, a recipe's `default path:` and `path source:`, a recipe's `inputs:` block and a `.spitout`'s `source_paths:`, quoted paths, and `#` comments are each highlighted distinctly. Placeholders SPIT defines itself are colored as built-ins, apart from the ones a pipeline names: `{@product}`, `{@entities}` and `{@stage}` in a path, `{@key}` and `{@value}` in a `default entities:` spelling, against a dimension such as `{sub}`, with the brackets of an optional `[...]` group marked and `[[` and `]]` as literal brackets; and `{@output}`, `{@cores}` and `{@here}` in a command, against a named port such as `{dwi}`, and `{@path}` in a `check`, against its parameters such as `{n}`. A `check` declaration's name and each check named in `@check(ndim(3), nonempty)`, on a port or a source, are marked as checks, and the port list carries on past their parentheses; a `default check:` line marks its checks the same way, with the `!` that drops one. A `review` declaration's name, each review named in `@review(looked_at)` on a port, an output or a source, and those in a `default review:` line are marked as reviews, with the `!` that drops one; a recipe's `review looked_at from qc/looked_at.csv` marks the review and its file. An output's folder and name, `{image.dir}` and `{image.stem}`, mark `.dir` and `.stem` apart from the port, as do `{@output.dir}` and `{@output.stem}` for the unnamed output. An input's values of a dimension, `{durations.digit}`, mark the dimension after the `.` as a dimension. A `@scalar(tr, min=5, max=100)` in a command or `verify` line, the number an input's file holds, is marked as a built-in, with its port, and its `min=` and `max=` bounds and their numbers; quoted, it is text. A `@join(images)` or `@list(images)`, a `many` input's paths as one argument or a file listing them, is marked the same way, with its port, a dimension after a `.` (`@join(images.run)`), and the quoted separator a join may give (`@join(images, "; ")`); quoted, it is text too. Lines inside a `stage`, a `default:` block or a keyword block such as `source:` fold with it, a new line after such a header, or after an operation header ending in `:`, is indented, and each entry of a keyword block is highlighted as its keyword's statement would be, a command's continued lines included. A `command name:` with nothing after its `:`, or a `command:` block's `name:` entry, holds a command on each line beneath it, run in order, and each of those lines is highlighted as a command, its `<` and `>` included.

Operation input and named output lists can span lines. The grammar keeps port,
type, check and extension highlighting through each list's closing `)`, including
nested generic types. Indent ports beneath the declaration; closing parentheses
may align with it. The compiler supplies diagnostic and hover ranges for the
original source lines.

Hovering shows what SPIT says about the text under the pointer. On one of SPIT's own words, such as `source`, `@vary(...)`, `beside`, `where`, `{@entities}`, `{image.stem}`, a command's `<` or `>`, a shape such as `{date:date}` or a `.spitout`'s `sources:`, it shows an example, a summary from the [language reference](https://github.com/eclnz/spit/blob/main/docs/language-reference.md), and a link to the section. On a pipeline's product or operation, it shows what the compiler knows: its signature, inferred type and dimensions, the steps that make and use it, its command, and its path rule. Both come from the same `spit check --hovers` run as the diagnostics, so SPIT decides what each word is: a product called `each` is not the selector, and nothing in a comment is explained.

`{@entities}` is spelled by a `default entities:` line, such as `default entities: {@key}_{@value} separated "-"`, in the file, a stage or a recipe, and a dimension's label is changed with `default entities sub: subject`. The line marks `{@key}` and `{@value}` as built-in placeholders, and aliases distinguish a dimension from its path label. No product may take a keyword's name, such as `entities`, `root`, `output` or `check`, so a line that starts with one is highlighted as that keyword.

In a `.spitout`, semantic highlighting reads the records themselves, coloring each source product, and each dimension and value in its brackets, by role. Pipelines and recipes get full keyword and structural coloring from the syntax grammar.

Each file is checked on its own with `spit check <file> --json --stdin --hovers`, which reads no data. A pipeline is compiled and may locate its data with one top-level `root` and source path rules, and name where its jobs write with one `output` line; a recipe can inherit either. A root, an output root or explicit source paths declared in both files are errors. All selection rules, including literal exclusions, stay in `.spitin`; an `inputs:` block, a `require`, `exclude` or `review ... from` rule, or a `sources:` record, written in one is an error, since those belong in a recipe and a `.spitout`. A recipe is checked against the pipeline its `pipeline analysis.spit` line names, so a rule naming an unknown source, or counting a dimension the source lacks, is marked on the rule, and a `root` line naming a folder that is not there is marked with a warning. Pipeline errors found during a recipe check are marked in the pipeline file. An error in a library a pipeline imports with `use` is marked in the library file, at its own line, and carries the `use` line that reads it, one for each file along a chain of imports, as related information labelled `imported here`; a library's marks go as soon as a check no longer reports them. SPIT gives each file by its path from the checked file's folder, so a library need not be open to be marked. Saving a pipeline rechecks the open recipes and the pipelines that import it. When a pipeline checks clean, each step whose output path no rule writes in full shows that path at the end of its line, such as `→ derivatives/yield_table/region={region}.csv`, with any extension its operation or `default ext:` adds, its `[...]` groups kept or dropped, and `{@entities}` written out for each product shape as its `default entities:` spells it, as `→ out/sub-{sub}/sub-{sub}_merged.img`. A step with several outputs names each one. Hover the product name for its type, producer and path-rule details. The hints are VS Code inlay hints, so `editor.inlayHints.enabled` turns them off. A `.spitout` is checked for the syntax of its records only: finding and settling a dataset's inputs is `spit inputs`, run from the command line.

It checks unsaved text after a short pause and reports syntax errors throughout the file. Once the syntax is valid, it reports every semantic, command, and path error, each on its related line, and shows warnings for likely mistakes such as unused definitions. Each problem underlines the text it is about, such as a misspelled input or one `{placeholder}`. An error in a step that a call to an operation carried out by steps makes is marked at the call, and lists the call and step in the body it came from, often in a library, as related information that links to each line; with an older SPIT build that reports no columns, the whole line is marked.

The extension reads JSON diagnostics from `spit check` even when validation exits 1. If the process fails without valid diagnostics, it shows a process failure instead.

## Operation and product hovers

Hover over an operation or product in a `.spit` pipeline to see what the compiler knows about it, including qualified references to imported definitions.

- Operation declarations show their generic signature and body, or their primitive matching behavior and command/verification templates. Calls show concrete port/product mappings and inferred types; composites show one concrete expansion instead of repeating their generic body. Primitive calls retain execution templates, type bindings and selector explanations. Long signatures and multiple outputs are laid out at port boundaries; bindings and expansions are grouped into code blocks.
- An operation carried out by steps, its header ending in `:` and its steps indented beneath it, lists those steps. At a call to one, the hover also lists the steps this call expands to, each argument names the input it supplies, and a product the call makes names the call and the step that writes it.
- Products show their inferred type and dimensions, a declared type only when it differs from inference, producing step, consuming steps, stage, and effective path template. The path explanation names an explicit rule, inherited stage default, pipeline default, or built-in output default. Sources without a pipeline path rule say that a recipe or inventory must supply it. Broken steps explicitly report unavailable inference. A product with many consumers lists eight readers and counts the remainder.

For example, `cleaned = clean(raw)` with `source raw : Frame<Native> [sample]` and `operation clean(frame: Frame<S>) -> CleanFrame<S>` shows `S = Native` on the call and `cleaned: CleanFrame<Native> [sample]` on the product.

Hovers use unsaved text and share the cached compiler check with diagnostics. Saving an imported pipeline refreshes dependent hovers. Independently valid declarations remain available while another line is broken; failed steps do not claim inferred types. Path templates describe artifact families; concrete dataset paths and filesystem checks are not part of these hovers. Recipes and inventories retain their existing diagnostics/highlighting without pipeline hovers.

Rebuild the sibling SPIT compiler with `cargo build`: hovers require its `check --json --stdin --hovers` support. The hovers appear in a VS Code Extension Development Host running this version of the extension.

## Try it locally

1. Build the [SPIT compiler](https://github.com/eclnz/spit) with `cargo build`.
2. Open this repository in VS Code.
3. Choose **Run > Run Without Debugging** (Control-F5 on macOS) to launch an Extension Development Host. It opens `../spit/examples/types/typed.spit` automatically.
4. Hover over `clean` or `cleaned` on the `cleaned = clean(raw)` line. The operation hover should show `S = Native`; the product hover should show `CleanFrame<Native>`. Edit the file to see diagnostics in the editor and Problems panel.

The extension uses a build at `../spit/target/debug/spit` if present, then tries `spit` on PATH. Set `spit.executablePath` in your user settings to use a build elsewhere; workspace settings cannot change it. It is the only setting. The extension stays off in folders VS Code does not trust. The SPIT executable needs `check <file> --json --stdin --hovers`, including for a `.spitin` and a `.spitout`.

The extension verifies the executable with `--version` before checking a file. The status bar shows the version of the SPIT that checked the open file, and its path on hover; **Output → SPIT Compiler** shows the same. It requires SPIT's descriptive version line, `SPIT (Simple Pipeline in Text) compiler, version 0.4.1`, and a SPIT at least as new as the extension, whose version follows SPIT's: this release needs SPIT 0.4.1 or later. Two builds can report the same version, so when the sibling debug build is older than a file of `../spit/src`, `Cargo.toml` or `Cargo.lock`, the file's first diagnostic is a warning naming the changed file and saying to run `cargo build`, and the status bar shows a warning sign.

A recipe groups dataset-specific source paths in `inputs:`. Indented `source: path`, `default: path`, and repeated `contexts: directory-pattern` entries highlight their names and path captures. Requirements count sources or exact context domains, as `require [sub] where contexts[sub,ses] count>=2`; `require [] where lut count=1` checks a global lookup. Inventories use unnamed `contexts:` sections.

## Test

Run `npm install`, then `npm test` with a sibling SPIT build. The grammar tests tokenize SPIT text with `vscode-textmate`, the engine VS Code uses, and are skipped until it is installed. Set `SPIT_TEST_EXECUTABLE` to another SPIT binary path if the repositories are elsewhere. A grammar test reads SPIT's keywords from `spit keywords` and fails when SPIT has a keyword the grammar does not colour, or the test lists one SPIT no longer has.
